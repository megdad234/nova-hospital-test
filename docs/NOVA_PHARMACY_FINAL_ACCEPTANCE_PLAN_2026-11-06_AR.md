# NOVA Hospital — خطة إغلاق ملاحظات الصيدلية قبل تسليم Windows
تاريخ: 2026-11-06. الحالة: خطة عمل، وليست شهادة إنجاز.

## قواعد غير قابلة للكسر
- المشروع NOVA فقط؛ لا تغيير في قواعد MedForce أو مشاريع أخرى.
- الحفاظ على منطق مرتجعات الصيدلية وطباعة إيصالاتها الناجحين؛ تعديلات عرض المرتجع فقط.
- لا تعديل بيانات المخزون أو الفواتير التاريخية عند تعديل سعر البيع.
- صلاحيات وتدقيق لجميع عمليات التغيير؛ لا تعديلات مباشرة من واجهة بلا صلاحيات.
- قاعدة بيانات مركزية LAN، عمل دون إنترنت، نسخ احتياطي قبل ترحيل المخطط، تثبيت/تحديث Windows سهل.

## نتائج الفحص الأولي المؤكدة
- صور الجهاز: تحصيل الفترة والمعاينة 80mm ظاهرتان، طباعة الورق غير مؤكدة.
- صور الجهاز: المرتجع الكامل أحمر بلا زر، الجزئي أصفر بزر؛ لا مساس بالمنطق.
- صور الجهاز: POS التأمين عبارة عن حقول قديمة ومربع تنبيه منفصل، ومساحة السلة كبيرة/خيارات الدفع تحت التمرير.
- صور الجهاز: شاشة الأسعار تعرض 1867 صنفاً كسجل مسطح مع أسعار صفرية، بلا إدارة سهلة.
- صور الجهاز: المخزون يعرض تشغيلات وحركات بأسماء تقنية ولا يوفر تحرير سعر البيع.
- فحص المصدر: `.github/ci/nova_batch15_bulk_prices.py` يوفّر معاينة/اعتماد/تراجع بأسعار الموردين؛ `.github/ci/nova_batch12_insurance.py` يربط التأمين بالمستفيد والعقد؛ `.github/ci/nova_batch09_pos_admin.py` يدمج واجهة POS والتحصيل. هذه الوظائف أساس لإعادة استخدام المنطق.
- GitHub Actions نجح لآخر تعديل POS `1973c703`، ولا يثبت التشغيل البصري على Windows.

## التنفيذ المطلوب — دفعة مترابطة
### P0: شاشة البيع والتأمين
1. تدقيق DOM الفعلي من ملف المصدر المستخرج، وليس التخمين بأسماء CSS/IDs.
2. وضع مباشر/تأمين حصري: إخفاء حقول العميل والتغطية القديمة في المباشر، إظهار اختيار العميل عند الآجل فقط.
3. بطاقة تأمين واحدة أعلى السلة: الجهة والعقد، البحث بالاسم/البطاقة، اختيار المستفيد، التحقق من الأهلية، تسجيل مستفيد جديد مع منع التكرار.
4. تفصيل حصة الجهة/المريض من الحساب الفعلي للعقد؛ عدم استخدام نسب افتراضية أو احتساب مطالبة كتحصيل نقدي.
5. سلة أدوية ذات ارتفاع محدد وتمرير داخلي حتى وهي فارغة؛ خيارات الدفع وزر التأكيد ظاهرة دون تمرير طويل.
6. اختبارات: مباشر، تأمين، آجل، مختلط، تعليق/استرجاع، أخطاء API، البحث المتزامن، منع انتقال بيانات المريض.

### P0: إدارة الأصناف والمخزون
1. فصل «إدارة الأصناف» عن «التشغيلات» و«حركة المخزون» بتبويبات، بحث بالاسم/الباركود وتصفح صفحات.
2. بطاقة صنف تعرض الاسم، الباركود، سعر الشراء/البيع، الوحدات، الرصيد والتشغيلات والصلاحية.
3. تعديل سعر البيع عبر مسار API موجود ومصرح له أو إضافة endpoint آمن عند الضرورة، مع تحقق قيم وتدقيق المستخدم والسعر القديم/الجديد.
4. تحديث الأسعار لا يمس الكميات أو سعر شراء التشغيلات أو فواتير الماضي؛ منع تحرير صلاحية تشغيلة دون سجل تدقيق مستقل.
5. تعريب أنواع الحركات sale/purchase/return_quarantine وغيرها، وتحسين التاريخ/الوقت.
6. اختبارات الصلاحيات، سعر صفر، سعر سالب، رصيد غير متغير، سجلات التدقيق، الاسترجاع.

### P1: الأسعار والبرايسات
1. أربع مناطق: أسعار الأدوية؛ استيراد برايس؛ مراجعة واعتماد؛ تاريخ وتراجع.
2. بحث/تصفية بالاسم والباركود والأسعار الصفرية، صفحات 25-50 بدلاً من 1867 صفاً دفعة واحدة.
3. استخدام API المعاينة والمطابقة والاعتماد والتراجع الموجودة، وعدم اعتماد تلقائي عند رفع الملف.
4. إظهار الأسعار القديمة والجديدة والفروق والمطابق وغير المطابق، مع اختيار الصفوف وتأكيد الحفظ.
5. لا تحديث تاريخي للفواتير، ولا كميات أو حركة شراء وهمية.

### P1: المرتجعات والإدارة والطباعة
1. تثبيت عرض الأحمر «تم الاسترجاع» والأصفر «مرتجع جزئي» دون تغيير منطق المرتجع.
2. تنسيق تواريخ الفواتير والحركات بشكل مقروء.
3. الإبقاء على معاينة تحصيل الفترة؛ اختبار الورق 80mm عملياً، والتأكد من هوامش الطابعة.
4. اختبار إيصالات الصيدلية السابقة كحالة رجوع إلزامية.

### P0: بوابة التسليم
- تحقق Python/JS، واختبارات API والتكامل، واختبار واجهات POS/التأمين/المخزون/الأسعار.
- بناء Setup.exe في GitHub Actions ثم التحقق من Artifact وSHA، وتثبيت نظيف وتحديث فوق نسخة سابقة مع نسخة احتياطية.
- تجربة التشغيل المحلي وLAN والطباعة الفعلية والنسخ الاحتياطي والاستعادة.
- التسليم برابط artifact واضح + رقم commit + نتائج الاختبارات + نواقص موثقة؛ لا إعلان «جاهز للاعتماد» قبل الاختبار الميداني.

## معيار الإغلاق
كل بند يحتاج: تغيير مصدر محدد، اختبار آلي ناجح، ثم لقطة/تجربة Windows للمسارات المرئية. نجاح CI وحده = جاهز لتجربة المستخدم، لا اعتماد مستشفى.
